### INK 裁決推導出的設計（待寫入 INK ADR）

#### 1. 取樣點格式（INK-1＝B ＋ tilt）

保留 tilt、且粗細可由**速度**驅動，因此 `timestamp` 也不能丟（速度＝位移／時間）。
搭配 INK-2＝C，`x` 存正規化比例：

| 欄位 | 型別 | 位元組 | 說明 |
|---|---|---:|---|
| `x` | uint16 | 2 | 正規化 0–1 對應 Block 寬度；精度為寬度的 1/65536 |
| `y` | int16 | 2 | 相對 Block 頂部，0.01mm 定點，範圍 ±327mm |
| `pressure` | uint8 | 1 | 256 階 |
| `tilt_altitude` | uint8 | 1 | 0–90°，精度 0.35° |
| `tilt_azimuth` | uint8 | 1 | 0–360°，精度 1.4° |
| `dt` | uint16 | 2 | 距筆畫起點的毫秒差，單筆上限 65 秒 |
| **合計** | | **9** | 10 萬點／頁 ≈ **900 KB** |

若 azimuth 的 1.4° 不足（例如書法筆刷對筆尖方向敏感），改 uint16 → 每點 10 bytes。
**這是 ADR 要裁決的精度問題，不是實作細節。**

#### 2. 筆刷是獨立實體，幾何是衍生資料

「恆寬／壓力驅動／速度驅動」與「可自訂平滑度」意味著**筆畫的外框不能存起來**——
它必須由「原始取樣點 ＋ 筆刷參數」即時算出，否則改筆刷設定時舊筆跡不會跟著變。

```text
InkStroke {
    stroke_id
    brush_id          -> BrushStyle（獨立實體、穩定 ID）
    anchor { block_id }
    samples[]         -> 上表格式
}

BrushStyle {
    width_mode: Constant | PressureDriven | VelocityDriven | Both
    base_width
    pressure_curve    // 壓力 -> 粗細倍率
    velocity_curve    // 速度 -> 粗細倍率
    smoothing         // 平滑度
    tilt_response     // tilt -> 筆尖形狀／方向
}
```

**這使 INK-1 選 (B) 而非 (C) 成為必要而非偏好**：曲線簡化會破壞速度資訊，
而速度現在是粗細的輸入。(C) 在這組需求下本來就不成立。

#### 3. INK-3＝A 與可自訂筆刷之間有 FND-0001 風險

外殼完全擁有繪製中筆跡（INK-3＝A），但抬筆後由核心持有並渲染。
若「取樣點 ＋ 筆刷參數 → 外框」這個函式在外殼與核心**各有一份實作**，
兩邊必然分岔——而分岔的形式是**抬筆瞬間筆跡外觀跳變**，且不會有任何錯誤。
這正是 FND-0001「一條規則只能有一個實作」要擋的東西。

三個選項（**需裁決**）：

- **(A) 外框函式只在 C++ 實作，經 FFI 暴露給外殼繪製繪製中筆跡**
  —— 單一實作，抬筆無跳變。代價：繪製中的每一幀都要跨 FFI。
- **(B) 接受抬筆時的視覺跳變**，外殼用簡化預覽
  —— 最省事，但使用者看得到筆畫「變形」。
- **(C) 改 INK-3 為 B**（核心持有暫存筆跡）
  —— 繪製與提交都由核心渲染，但推翻已裁決的 INK-3。

#### 4. INK-4 的框選需要第三種 selection 型別，與 EDT-1＝B 衝突

框選筆跡並刪除需要 ink selection。EDT-1＝B 只有文字區間與空間集合兩種，
且其裁決明文要求「擴充條件必須寫進 ADR」。

**中間路線（建議）**：把 ink selection 定義為**受限 selection**——
只支援刪除與移動，不進入完整操作集合（不支援樣式套用、不支援跨型別複製貼上等）。
這樣 EDT-1 擔心的「型別數量是成本的乘數」被限縮：
乘數只作用在兩個操作上，而不是全部操作。

#### 5. 像素擦必須是幾何運算，不能是點陣

「像素擦」在向量筆跡上有兩種實作：

- 把圖層點陣化後擦像素 —— **與可自訂筆刷直接衝突**：點陣化後就不能再依筆刷重算外框
- 以圓形筆頭做幾何相減，產生多段子筆畫 —— 保留向量性

因此**像素擦實為細粒度的分段擦**，三種橡皮擦（分段／像素／整段）共用同一個底層運算，
差別只在擦除形狀與粒度。這在 ADR 裡應寫明，否則會被實作成兩套機制。

#### 6. Undo 深度：建議改用記憶體預算，不用筆數

「趨近無限、session 內保留」在 COW 之下**大致可行**，但**筆數限制在這裡是錯的度量**：

| 一個 undo 項目 | 實際成本 |
|---|---|
| 打一個字 | COW 路徑複製 ~3 節點，約 2 KB |
| 畫一筆手寫 | 10,000 點 × 9 bytes ≈ **90 KB** |

**差距 45 倍。** 用筆數設限會導致：純文字工作時上限形同虛設，
而手寫密集時記憶體暴增。

**建議：以記憶體預算設限（例如 256 MB），超過時丟棄最舊項目。**
理由是它直接對應真正的稀缺資源。預算值應為可調參數，
並在 UI 上可觀察（讓使用者知道 undo 歷史被截斷了）。

補充：「session 內保留、不跨檔案開關」大幅簡化設計——undo 歷史不需要序列化。

### 由裁決推得、需寫進 ADR 的連帶條件

- **EDT-1＝B 使 INK-4＝C 不成立**：ink 套索需要第三種 selection 型別。
  若之後要 INK-4＝C，必須先重開 EDT-1 並寫明擴充理由。
- **TXT-3＝A ＋ BND-2＝A 相互支撐**：組字覆蓋層走同步通道，時序最單純。
  若將來 BND-2 改為非同步，TXT-3 的契約要重新檢查。
- **EDT-4＝A（全域單序列）與 EDT-2＝A（單層原子 transaction）一致**：
  跨容器操作是一個 transaction、落在一條序列上，沒有語意破碎。
- **ATH-2＝A 要求在該格式的決策裡明文寫「此格式將被丟棄」**（README 明文要求），
  否則會被誤當正式格式沿用。
- **INK-4 的框選與 EDT-1＝B 衝突**，需以「受限 selection」化解或重開 EDT-1（見上）。
- **INK-3＝A 與可自訂筆刷有 FND-0001 風險**，外框函式必須只有一份實作（見上）。
- **ATH-2＝A 的檔案格式必須能存 InkStroke 與 BrushStyle**：
  即使是「可丟棄的簡陋格式」，也得涵蓋手寫，否則 dogfood 無法驗證手寫路徑。

| 編號 | 裁決 | 必須保留的驗證與重開條件 |

  保留，但手寫輸入、擦除、lasso 與 Ink undo 不得成為 P1 垂直切片的 blocker。
- **P1.5 的可丟棄格式現在確定方向，但延後到最小 `ParagraphRecord` 與原子 `Transaction` 完成後
  才實作。** 這不推翻 ATH-2＝A；目的是避免在正式內容模型不存在時先做一次必然重寫的 codec。
- P1.5 格式仍須明文標記會被 authority 格式取代；若 P1.5 dogfood 納入手寫，格式也必須涵蓋
  `InkStroke` 與 `BrushStyle`。

## 03-text（TXT）

> **README 已過時**：其中「第一版以 DirectWrite 實作」是在跨平台需求確立前寫的。
> Windows＋Linux＋iPad 的硬需求已使原生 API 路線出局（會變成三套 shaping 實作）。
> 寫 ADR 時應一併更正。

### TXT-1【你決定】字型 fallback 的策略放哪裡？

HarfBuzz 不做 fallback（Spike 5 已確認：Segoe UI 無 CJK 時整段 `.notdef`）。
「哪個字元用哪個字型」必須有人決定，而字型清單本質是平台資源。

- **(A) C++ 定 `FontProvider` 介面，平台只提供字型清單，挑選邏輯只有一份在 C++**
- (B) 平台各自實作完整 fallback，C++ 只收結果
- (C) 綁定固定字型集合隨程式散布，不使用系統字型

**我建議 (A)**：fallback 挑錯是靜默錯誤（字顯示成豆腐或換了字型，不會報錯），
依 FND-0001 應在 C++ 且只有一份實作。(B) 會產生三套挑選邏輯必然分岔。
(C) 可攜性最好但體積暴增且無法涵蓋使用者自訂字型。

**代價**：(A) 仍需每平台一層薄的字型列舉實作，那是無法避免的。

### TXT-2【你決定】斷行政策層的範圍

libunibreak 給的是 UAX #14 的**候選**斷點。實務上要再過濾——Spike 6 實測 URL
`https://example.com/path` 內部有 2 個候選斷點，多數編輯器會抑制。

第一版要支援哪些政策？（可複選）

- (A) 只用 UAX #14 原始結果，不加政策
- (B) ＋ 抑制 URL／路徑內部斷行
- (C) ＋ 數字與單位之間不斷（`100 kg`）
- (D) ＋ 使用者自訂不斷空白（NBSP 等已在 UAX #14 內，此指額外的自訂機制）

**我建議 (A)＋(B)**：URL 斷行是使用者最容易察覺的錯誤。(C) 的規則在 CJK 語境下界定困難，
(D) 需要文件模型支援（字元級屬性），會擴大 `01-document` 的範圍。

### TXT-3【你決定】IME composing region 的模型可見度

README 說「IME 狀態由外殼擁有，但組字文字會佔空間、影響換行與游標位置，因此核心必須看得見」。
兩者張力需要裁決：

- **(A) 核心持有 composing region 作為「非權威覆蓋層」**——參與版面計算，但不進 ObjectStore、
  不進 undo，確定時才成為真正的內容
- (B) 外殼把組字文字當一般文字送進核心，確定時再標記 undo 邊界
- (C) 核心不知道組字，外殼自行疊加顯示

**我建議 (A)**：(B) 會讓組字中的文字進入權威狀態，undo／協作／持久化都要處理「半個字」。
(C) 則外殼必須自己做版面（違反「邊界是 display list」）。

**這題影響最大**：注音輸入是第一驗收場景（README 明文），選錯要重做 `01-document`、
`04-editing`、`07-binding` 三處契約。

### TXT-4【我建議，可否決】shaping 結果的快取鍵

- **(A)** `{文字內容 hash, 字型集合 revision, 字級, 語言/script}` 為鍵，LRU 快取
- (B) 不快取，每次重新 shape

**我建議 (A)**。已有 `SnapshotId`（LAY-0002 D18）可掛字型環境 revision。
未回覆則照此實作，但**容量與淘汰策略留為 benchmark 參數**，不寫死。

### TXT-5【該量測，不該裁決】shaping 的延遲預算佔比

LAY-0001 定同步路徑 p99 ≤ 3ms。shaping 佔多少目前**沒有任何數據**。
應在 `bench_flow_sequence` 之外另建 shaping benchmark 後再定，不現在猜。

## 04-editing（EDT）

### EDT-1【你決定】第一版支援幾種 selection 型別？

README 明文：「每多一種，所有操作都要對它定義行為——型別數量是成本的乘數」。

- (A) 只有文字區間（一維、有序）
- **(B) 文字區間 ＋ 空間節點集合（無序）**
- (C) (B) ＋ ink 幾何套索

**我建議 (B)**：畫布是結構化節點的空間排版，與文件共用 selection／undo（
`substrate-extraction-pivot` 已定），因此空間集合躲不掉。
ink 是獨立圖層、不共用 selection，(C) 可延後。

**擴充條件必須寫進 ADR**：什麼情況下才允許加第三種。

### EDT-2【你決定】跨型別 transaction 的原子性怎麼表達？

「把文字移到畫布」＝ 文件刪除 ＋ 空間新增，必須不可分割。

- **(A) 單一 `Transaction` 物件內含多個 typed command，全成功或全拒絕**
- (B) 巢狀 transaction（可嵌套的 begin/commit）
- (C) 兩階段提交

**我建議 (A)**：已有 `DocumentRevision::validate()`（D12）作為發布前的全域驗證點，
單層 transaction ＋ 原子發布就足夠。(B)(C) 的複雜度需要協作場景才划算，那不在第一版。

### EDT-3【你決定】undo 合併規則的三類共存

README 列出三種行為：文字合併、空間物件不合併、一筆手寫是一個單位（內含數千點）。

- **(A) 每個 command 型別自己宣告「可否與前一個合併」，undo stack 只問不猜**
- (B) undo stack 依時間窗統一決定
- (C) 外殼決定邊界

**我建議 (A)**：(B) 無法表達「空間操作永不合併」。(C) 違反 FND-0001 第 6 條
（不得依賴外殼自律）。

### EDT-4【你決定】undo 的範圍是全域還是每容器？

- (A) 整份文件一條 undo 序列
- (B) 每個 Container 各自一條
- (C) 全域一條，但記錄影響範圍供 UI 提示

**我建議 (A) 或 (C)**。(B) 在跨容器操作（EDT-2 的例子）時語意破碎——
一個原子操作會落在兩條序列上。**這題我沒有強烈偏好，(C) 的額外成本不高但要你決定值不值得。**

### EDT-5【該量測，不該裁決】undo 時間窗的閾值

README 已定「參考 VS Code 約 1 秒」為初始值，但明文是 benchmark 參數。
應在有真實打字 workload 後量測，不現在定死。

## 05-ink（INK）

> **本領域依 README 的流程例外由人類主導**，我只整理選項，不提供「照建議做」的預設。
> 以下全部標記為【你決定】。

### INK-1【你決定】取樣點的儲存格式

一頁可到數十萬點，每點含 `x, y, pressure, tilt, timestamp`。

- (A) 完整保留所有欄位與所有點（最忠實，最大）
- (B) 量化：座標定點數、壓力 8-bit、丟棄 tilt、timestamp 改為相對差值
- (C) (B) ＋ 抬筆後做曲線簡化（Ramer–Douglas–Peucker 之類），只存簡化後的點

**取捨**：README 已定「品質門檻是意圖捕捉，不是繪圖產品」。若接受該前提，(B) 或 (C) 合理。
但 (C) **不可逆**——簡化掉的資訊救不回來，將來若想提升手寫品質必須重做資料。

### INK-2【你決定】anchor 的內部表達

中心落點歸屬已定，但邏輯錨點型別未定。

- (A) `BlockId` ＋ Block 內相對座標
- (B) `BlockId` ＋ 相對於 Block 內某個字元位置的偏移
- (C) `BlockId` ＋ 正規化比例座標（0–1）

**相關**：README 已接受「reflow 可能造成筆跡與文字錯位，不自動修復」。
(B) 會讓錯位變小但引入「字元位置」依賴，與「ink 是獨立圖層」的前提有張力。
(C) 與已定的「全寬切換時水平等比拉伸」最一致。

### INK-3【你決定】繪製中筆跡的「兩個真相」契約

抬筆前筆跡不在模型裡，但畫面上已存在。

- (A) 外殼完全擁有繪製中的筆跡，核心零知情，抬筆才提交
- (B) 核心持有「暫存筆跡」槽位，參與 hit-test 但不進 undo／持久化
- (C) 每個取樣點即時進模型

**取捨**：(A) 最簡單但繪製中無法做任何核心側判斷（例如即時判斷跨越哪個 Block）。
(C) 每秒數百次 transaction，成本高且 undo 語意破碎。

### INK-4【你決定】ink 是否需要獨立的 selection／編輯

前提已定「自由筆跡是獨立圖層，不共用 selection」。但仍需釐清第一版是否支援：

- (A) 完全不支援選取／移動／刪除單筆，只能整層清除
- (B) 支援刪除單筆（橡皮擦），不支援選取移動
- (C) 支援套索選取與移動

（此題與 EDT-1 的 (C) 連動。）

## 07-binding（BND）

### BND-1【我建議，可否決】display list 的緩衝區所有權

- **(A) 核心擁有雙緩衝，外殼取得唯讀 span，下一幀前有效**
- (B) 每幀重新配置，外殼負責釋放
- (C) 外殼提供緩衝區，核心填入

**我建議 (A)**：(B) 每幀配置在 8.33ms 預算下是浪費。(C) 讓外殼決定容量，
容量不足時的降級路徑複雜。(A) 的代價是核心要維持雙份記憶體。

未回覆則照 (A) 實作。

### BND-2【你決定】command 通道是同步還是非同步？

外殼送入鍵盤／IME／指標事件。

- (A) 同步：外殼呼叫、核心處理完才返回，回傳新的 display list
- (B) 非同步：事件入佇列，核心處理後通知外殼取結果
- (C) 混合：輸入事件同步（要求低延遲），其餘非同步

**取捨**：(A) 最單純且延遲最低，但核心處理時間直接變成 UI 執行緒的阻塞。
LAY-0001 已定同步路徑 p99 ≤ 3ms，若守得住，(A) 成立。
(B) 需要外殼處理「畫面比輸入落後」的中間狀態。

**這題與 TXT-3 連動**：IME 組字若走同步，時序簡單得多。

### BND-3【我建議，可否決】版本不符的行為

README 已定「必須 fail closed」。剩下的是形式：

- **(A) display list 開頭帶版本號，不符則核心拒絕產出並回傳明確錯誤，外殼顯示升級提示**
- (B) 核心嘗試向下相容舊版格式
- (C) 直接 abort

**我建議 (A)**。(B) 會累積相容性分支，且「部分相容」是靜默錯誤的溫床。
(C) 對使用者是無法診斷的當機。

### BND-4【你決定】FFI 的錯誤傳遞粒度

FND-0002 已定 C ABI 的錯誤模型。此處要決定的是**外殼收到錯誤後的契約**：

- (A) 任何核心錯誤都是不可恢復的，外殼只能顯示錯誤並終止 session
- (B) 區分可恢復（如版面暫時失敗，可重試）與不可恢復（如狀態損壞）
- (C) 核心保證不回傳錯誤，所有失敗都在核心內部 fail-fast

**我建議 (B)**，但這牽涉產品體驗（使用者遇到錯誤時能不能保住未存檔的工作），
因此標為你決定。

### BND-5【該量測，不該裁決】display list 的封送成本

Spike 2 已測過 FFI 邊界延遲（p99 0.42ms），但那是在目前的資料結構完成**之前**。
應在 display list 格式定案後重測，不現在裁決其形狀。
