# FND-0001：Krepis 的範圍、語言邊界判準與拒絕清單

## 狀態

Accepted

## 日期

提出：2026-08-16
接受：2026-08-16

## 背景

Krepis 由一個既有專案（Planist）抽取而來。該專案累積了 71 份決策與大量實作，但其中
**47,316 行會靜默出錯的邏輯位於使用者無法審查的語言**，而該專案的模型要求人類是核准者——
核准者讀不懂被核准的東西時，核准是儀式而非閘門。

同時該專案的規格制度只能增加承諾、不能減少承諾，導致 71 份決策中 `Rejected` 為 0、
16 份標著 rollout gate 未完成。

Krepis 從第一天就必須避免這兩件事，因此需要一份定義**什麼進、什麼永不進、以及憑什麼判斷**
的基礎決策。

## 決策

### 1. 範圍陳述

> Krepis 提供多平台、本地優先的**結構化筆記核心**：權威狀態、文件模型、版面、選取、undo
> 與 ink 資料模型。**不含任何特定產品的語意。**

### 2. 進庫的能力

authority（identity／session／permission／persistence／protocol／digest）、
文件模型（node tree／stable ID／schema／codec）、版面引擎（流式＋空間）、
selection／undo／typed transaction、ink 資料模型（不含繪製）。

### 3. 拒絕清單（永不進庫）

- 計畫語意與承諾追蹤
- repo binding、code locator
- workflow 定義與匯出
- 治理 bundle 的格式
- 導覽、入口與一切產品外殼決策

規格語意層（facet／relation／conformance／anchor 之類的治理詞彙）判為**庫之上的獨立包**，
不屬核心。

### 4. 判準

> **一個刻意平凡的筆記 app 需不需要這個決策？**
> 需要 → 進庫。只有特定產品需要 → 留在該產品。

第一個消費者 Notist 即為此判準的實體：它刻意不含規格工程與治理，因此任何漏進 Krepis 的
產品語意都會在 Notist 上顯得多餘。**Notist 變複雜就代表這道判準失效了。**

### 5. 語言邊界判準

語言邊界與**權威性**邊界重合，判準是**錯誤會不會靜默**：

| 性質 | 歸屬 | 理由 |
|---|---|---|
| 錯誤靜默（codec、狀態轉換、交易順序、版面計算、規則求值） | **C++** | 必須可人工審查；靜默錯誤沒有徵兆，直到資料已壞 |
| 錯誤可見（呈現、樣式、視覺回饋） | 平台外殼 | 一眼看得到，不需人工審查 |

### 6. 兩條結構性約束

- **client 在結構上無法成為權威。** 任何 client 判斷都要能被 Krepis 否決。
- **一條規則只能有一個實作。** 同一條規則若在核心與外殼各有一份，兩者必然靜默分岔。

### 7. 命名

產品一律以 `-ist` 命名；**基座不使用 `-ist`**。命名層級即區分基座與產品，
這是防止產品語意漏進基座的第一道防線。

## 這份決策關閉哪一道閘門

**「這段程式碼該寫在哪裡」原本沒有可判定的答案。**

本決策之後，該問題有兩道機械判準可回答：拒絕清單（第 3 節）與錯誤靜默判準（第 5 節）。
新增公開標頭、新增能力目錄、以及審查任何 PR 時，這兩道判準可直接判 pass／fail，
不需要重新討論產品定位。

## 被淘汰的方案

| 方案 | 處置 | 理由 |
|---|---|---|
| 全部以外殼語言撰寫，核心只做持久化 | 淘汰 | 會靜默出錯的邏輯留在無法審查的語言，等於沒有核准機制。這正是抽取的起因 |
| 全部以 C++ 撰寫，含呈現層 | 淘汰 | 呈現層的錯誤可見，付人工審查成本卻無收益；且 C++ UI 開發速度顯著較慢 |
| 不設拒絕清單，需要時再判斷 | 淘汰 | 基座吸收一切是抽庫最常見的失敗方式，而且是漸進發生的——沒有事前清單就沒有拒絕的依據 |
| 基座與產品共用 `-ist` 命名 | 淘汰 | 半年後無法從檔名分辨層級，混淆會直接導致產品語意漏進基座 |

## 後果

### 正面

- 「該寫在哪」與「該不該進庫」變成可機械判定，不需重新辯論定位。
- 使用者可審查全部會靜默出錯的程式碼，核准機制成為真實閘門。

### 負面

- 呈現層與核心分屬兩個語言，跨邊界的除錯比單一語言困難。
- 拒絕清單會在某些時刻顯得不便（「放這裡比較快」），**而它的價值正是在那些時刻拒絕**。
- 第 6 條「一條規則只能有一個實作」排除了以 client 快取規則做樂觀更新的常見做法，
  外殼的響應性必須以其他方式取得（見 `07-binding` 的後續決策）。
