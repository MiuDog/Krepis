# FND-0002：C ABI 邊界、錯誤模型、記憶體策略與執行緒模型

## 狀態

**Accepted**（D2–D5）

D1（同步／背景的分工線畫在哪）已分離至
[`LAY-0001`](../02-layout/LAY-0001-sync-background-split-and-frame-budget.md)，狀態 `Proposed`，
待 P0 實測後決定。**本決策的核准不包含 D1。**

## 日期

提出：2026-08-16
接受：2026-08-16（使用者同意將 D1 分離並核准 D2–D5）

## 背景

這幾項是同一個問題的數個面，**必須一起決定**。分開決定會產生互相矛盾的答案：

```
被 Dart FFI 呼叫  →  公開邊界是 C ABI  →  C++ 例外不得跨越  →  錯誤是回傳值
                                       ↓
                          display list 每幀產出  →  arena  →  生命週期契約進邊界
                                       ↓
                          背景執行緒  →  arena 需雙緩衝  →  邊界需執行緒親和性規則
```

`FND-0001` 已固定：公開邊界的形狀由「錯誤會不會靜默」決定，client 不得為權威，
**一條規則只能有一個實作**。本決策在該框架下具體化。

使用者於 2026-08-16 選定**背景執行緒**作為並行模型。

## 約束：以下三項不是決策

它們由外部事實決定，**沒有替代方案，核准與否不改變它們**。列出來是為了讓下方的決策
不必重複論證，也為了讓「同意」只針對真正的選擇。

| 約束 | 由什麼決定 |
|---|---|
| 公開邊界必須是 C ABI | Dart FFI 只支援 C ABI |
| C++ 例外不得跨越公開邊界 | 跨 C ABI 拋例外是未定義行為 |
| 核心不得從背景執行緒直接回呼外殼 | Dart isolate 是單執行緒；任意原生執行緒無法直接呼叫回 Dart |

## 本決策核准的四件

| # | 決策 | 選定 | 被淘汰的替代 |
|---|---|---|---|
| **D2** | display list 的**記憶體策略** | arena（bump），一份一塊、整塊丟棄 | 一般 heap：每幀數千次 malloc／free，且難以表達「外殼還在讀」 |
| **D3** | display list 的**生命週期契約** | **外殼明確釋放前有效** | 「下一幀自動失效」在背景執行緒模型下不成立（外殼可能仍持有前一份） |
| **D4** | 內部**錯誤型別**與 C++ 標準 | **C++20 ＋ 自訂最小 `Result<T, Error>`** | 升 C++23 用 `std::expected`：提高 Android NDK／Xcode 最低版本需求，只換到少寫一個小型別 |
| **D5** | **記憶體不足**的語意 | **terminate，不視為可恢復** | 視為可恢復會讓每個配置點多一條錯誤路徑，污染所有介面，而該路徑實務上永遠不會被正確測試 |

**D3 是本決策中風險最高的一項**：選錯不會立刻顯現，會在長時間執行後以記憶體成長的形式出現。
明確釋放把責任推給外殼，**漏放即洩漏**——因此外殼側必須有對應的測試（見「後果」）。

## 決策

### 1. 交付形式：公開邊界是 C ABI（約束）

- 公開標頭只使用 C 相容型別；**C++ 型別、模板、STL 容器一律不得出現在邊界上**。
- 核心物件以 **opaque handle**（不透明指標）暴露，外殼不得知其佈局。
- 進入點帶版本；核心與外殼版本不符時 **fail closed**，不嘗試相容。

C++ 仍是內部實作語言；**C ABI 只是邊界的形狀，不是實作的限制**。

### 2. 錯誤模型（邊界為約束；內部型別為 D4、OOM 為 D5）

| 層 | 語意 |
|---|---|
| **C ABI 邊界** | 每個函式回傳 typed status code，結果經 out-param 帶出。**邊界必須有 catch-all，任何例外都不得逃逸** |
| **內部：可恢復的失敗** | 自訂最小 `Result<T, Error>` |
| **內部：程式錯誤** | assert／terminate。不轉成錯誤碼——把 bug 偽裝成可處理的錯誤會讓它被靜默吞掉 |
| **記憶體不足** | terminate，不視為可恢復 |

`Error` 必須含**機器可判斷的 code**。呼叫者不得分析錯誤訊息文字。

### 3. 記憶體策略：arena，雙緩衝（D2、D3）

- display list 配置於 **arena（bump allocator）**：一份 display list 一塊 arena，
  用畢整塊丟棄，**不做個別釋放**。
- **雙緩衝**：外殼持有 A 進行繪製時，核心可在 B 建構下一份。
- **生命週期契約（進 C ABI）**：外殼取得的 display list **在其明確釋放該 handle 之前有效**；
  核心不得回收未釋放的緩衝。
- 一般物件所有權：預設值語意與 RAII、Rule of Zero；`unique_ptr` 表唯一所有權；
  `shared_ptr` **僅用於真正的共同所有權**，不作為方便的預設。

### 4. 執行緒模型：存在兩條路徑，且邊界只有一個執行緒

**本節只固定跨能力的部分。分工線畫在哪屬於 `LAY-0001`。**

- 核心存在**同步路徑**（於呼叫端執行緒執行）與**背景路徑**（核心內部工作執行緒）。
- **兩條路徑是同一份實作的兩種執行模式，不是兩份實作**（`FND-0001` 第 6 條）。
- **所有 C ABI 進入點只能由外殼的 UI 執行緒呼叫。** 背景執行緒是核心內部細節，永不跨越邊界。
- **核心不得直接回呼外殼。** 背景工作完成時只能經 Dart native port 送出訊號，
  由外殼在其 UI 執行緒主動拉取結果。
- **每一個公開函式的文件必須寫明其執行緒契約。**

「背景執行緒」**不表示所有版面都在背景執行**——若每次按鍵都需一次執行緒交接才會出現字，
那是可見延遲。實際分工見 `LAY-0001`。

## 這份決策關閉哪一道閘門

**在此之前無法撰寫任何公開標頭**，因為每個函式的形狀（回傳什麼、誰配置記憶體、
哪個執行緒可以呼叫、緩衝誰釋放）都未定。

本決策之後公開標頭可以開始撰寫，且新增介面時有機械判準可檢查：
是否為 C 相容型別、是否回傳 status code、是否標明執行緒契約、緩衝的釋放責任是否明確。

**D1 未定不阻擋此閘門**——分工線影響的是內部呼叫結構，不是邊界的形狀。

## 被淘汰的方案

| 方案 | 處置 | 理由 |
|---|---|---|
| 邊界用 C++ ABI | 淘汰 | Dart FFI 不支援；且 C++ ABI 跨編譯器不穩定 |
| 邊界拋例外，外殼接 | 淘汰 | 跨 C ABI 拋例外是未定義行為，不是風格問題 |
| 升到 C++23 用 `std::expected` | 淘汰 | 提高 NDK／Xcode 工具鏈版本需求，換到的只是少寫一個小型別 |
| 每幀重新配置 display list（一般 heap） | 淘汰 | 每幀數千次 malloc／free；且無法表達「外殼還在讀」的生命週期 |
| display list 契約為「下一幀自動失效」 | 淘汰 | 在背景執行緒模型下不成立——外殼可能仍持有前一份 |
| OOM 視為可恢復 | 淘汰 | 污染每個介面，且該錯誤路徑實務上永遠不會被正確測試 |
| 外殼做樂觀版面以掩蓋延遲 | 淘汰 | 那是版面規則的第二份實作，違反 `FND-0001` 第 6 條，必然靜默分岔 |
| 核心直接回呼外殼 | 淘汰 | Dart isolate 單執行緒，任意原生執行緒無法直接呼叫回 Dart |

## 後果

### 正面

- 公開介面的形狀有機械判準，新增介面時不需重新討論。
- arena ＋ 明確釋放責任使 display list 的生命週期可被測試驗證。

### 負面

- **C ABI 邊界是持續成本**：每個要暴露的能力都要手寫一層轉接，且不能用 STL 型別。
- **D3 把釋放責任推給外殼**。因此外殼側**必須**有「配置數等於釋放數」的測試，
  否則洩漏會在長時間 dogfood 後才顯現。**此測試是 D3 的配套條件，不是選配。**
- opaque handle 使外殼難以在除錯器中檢視核心狀態，需要額外的除錯輸出機制。
- 自訂 `Result` 是重複造輪子，且與未來可能的 `std::expected` 遷移有一次性成本。

## 待實測驗證的假設（P0 必須量）

1. 雙緩衝 arena 的交接成本可忽略。
2. Dart 端零複製讀取 display list 的實際成本與 GC 行為。

（原第 1 項「同步路徑能否在一幀內完成」已隨 D1 移至 `LAY-0001`。）
