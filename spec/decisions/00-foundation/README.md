## 待決問題

### 必須在 P1 之前定（會約束所有公開介面的形狀）

- **交付形式與 ABI**：Krepis 必須能被 Dart FFI 呼叫，而 **Dart FFI 只認 C ABI**。
  因此公開邊界是 C ABI，內部 C++ 型別不得出現在邊界上。
- **例外策略**：**C++ 例外不能跨 C ABI 邊界**，洩漏即為未定義行為。
  上一條直接推導出：邊界層必須有 catch-all，把任何例外轉為回傳值形式的錯誤。
  內部是否使用例外是獨立問題，但**邊界的形狀已被決定**。
  錯誤型別必須含機器可判斷的 code；呼叫者不得分析錯誤訊息文字。
- **記憶體策略**：版面每幀產出一份 display list。以一般 heap 配置意味著每幀數千次
  malloc／free；**arena（一幀一塊、幀末整塊丟棄）幾乎確定是對的**。
  這不是最佳化——它決定 display list 的生命週期契約（「本塊在下一幀開始前有效」），
  而該契約必須寫進 FFI 邊界。相關：`07-binding` 的所有權待決問題實為本題的下游。
- **並行模型**：版面是否在背景執行緒執行？
  單執行緒簡單，但長文件重排會卡住輸入；背景執行緒不卡輸入，但 display list 產生跨執行緒
  生命週期問題，且與 arena 策略衝突。
  **必須在 P1 之前定**——事後追加執行緒安全通常導致介面重寫。
