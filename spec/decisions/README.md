# Krepis 決策文件作業規範

## 適用範圍

本規範適用於以下決策領域的新 ADR 與後續增補：

- `00-foundation`
- `01-document`
- `02-layout`
- `03-text`
- `04-editing`
- `06-authority`
- `07-binding`

`05-ink` 是明確例外，依該目錄 README 的人類主導規則處理。

## 決策授權與選擇順序

在需求與限制已足夠明確時，AI 可以直接選擇方案並寫入 Proposed／Accepted 子決策，不必逐題等待
人類選項。評估優先順序如下：

1. 正確性、單一權威與 invariant 可證明性。
2. 演算法時間複雜度、最壞情況界線與工作量是否隨資料規模成長。
3. Snapshot、並行與記憶體生命週期安全。
4. 記憶體複雜度、cache locality、配置次數與資料搬移量。
5. 長期擴充性、跨模組一致性與能否避免第二份規則。
6. 實作與維護成本；只有前述條件接近時才作為主要 tie-breaker。

「全局最佳」是多目標判斷，不得偽裝成已量測事實。容量、fanout、門檻、延遲、吞吐量或平台成本
若必須實測才能知道，就保留為 benchmark 參數，不能用較容易實作作為替代答案。

以下情況仍必須停下來請人類決定：

- 產品語意或使用體驗存在多個合理答案。
- 決定會擴張 Krepis 的領域中立範圍。
- 缺少只能由人類提供的用途、風險承受度或裝置回饋。
- 方案優劣取決於尚未取得的實測數字，且沒有可逆的預設。

## 每份技術決策的必要內容

每份 ADR 或 Accepted 子決策必須依實際內容涵蓋：

1. **決策與適用邊界**：說清楚誰是 authority、哪些資料是權威、derived 或 cache。
2. **專業名詞**：定義本決策引入或依賴的術語，不能只列英文名稱。
3. **資料結構**：描述欄位、ownership、索引方向、生命週期與新舊 revision 如何共用。
4. **演算法流程**：依執行順序說明正常路徑、邊界路徑與失敗路徑。
5. **複雜度**：標明主要操作的時間／空間複雜度，以及成本受哪個變數控制。
6. **具體例子**：至少包含一個正常例子；有靜默風險時再加入邊界或錯誤例子。
7. **Invariant 與拒絕行為**：不一致時由誰拒絕、是否可重建，以及禁止 client 做什麼。
8. **後果**：記錄效能、記憶體、並行、測試與維護責任。
9. **未決參數**：把需要 benchmark 或平台證據的數值留在「尚未決定」，不要混入已接受設計。

若某一項確實不適用，可以省略，但不能省略真正存在的資料流、狀態轉移或失敗模式。

## 聚焦架構圖

凡決策涉及專業名詞、演算法流程、資料結構、狀態或跨執行緒交接，必須使用專案的
`focused-architecture-diagram` 規範，在 `docs/architecture/` 建立或更新聚焦文件：

- 資料查找、轉換與 ownership 使用 `flowchart`。
- 交易、執行緒交接與時間先後使用 `sequenceDiagram`。
- 生命週期與狀態轉移使用 `stateDiagram-v2`。
- 單張圖聚焦一個核心問題；不同問題拆成不同小圖或不同文件。
- 每張圖後必須用文字解釋節點責任、箭頭含義與失敗時的結果。
- 圖中使用的內部 handle、revision、index 或 queue 必須在同文件術語表定義。
- 文件必須包含可代入的具體資料例子，不能只畫抽象方塊。

ADR 保存「為什麼選」與不可違反規則；架構文件保存「資料如何流」與「演算法如何執行」。兩者必須
互相連結，不能只更新其中一邊。

## 偏離建議選項

若最終選擇不是討論中原先標示的建議方案，ADR 必須新增獨立的「偏離原建議」段落，至少記錄：

1. 原建議方案與未採用理由。
2. 新方案追求的全局優勢。
3. 新增的靜默錯誤、最壞情況、並行或記憶體風險。
4. 因此升級的機器測試、benchmark、sanitizer／race evidence 與人工審查清單。
5. 能使決策重新開啟的客觀條件，例如未達效能優勢、出現無法證明的生命週期或跨平台不成立。

偏離建議不能只寫「已接受風險」。每一項新增風險都必須對應可執行的驗證或明確的人類核准閘門。

## 寫入與驗證流程

1. 同一組同類型問題一次整理，避免逐題造成局部最佳化。
2. 每次接受後立即更新 ADR 狀態、日期、目錄 README 與相關架構文件。
3. 若決策增加實作風險，把測試或人工審查閘門同步加入 roadmap／task 文件。
4. 執行 Markdown read-back、連結與 Mermaid fence 檢查。
5. Mermaid CLI 可用時執行實際渲染；不可用時明確標記「未渲染驗證」。
6. 執行 `git diff --check`，並確認沒有殘留與新決策矛盾的舊敘述。

## 建議段落模板

```markdown
## Dn：<決策名稱>

### 決策與邊界

### 資料結構

### 演算法流程

### 複雜度

### 具體例子

### Invariant 與拒絕行為

### 後果與驗證

### 偏離原建議
```

只有實際偏離建議時才加入最後一節。術語表可以放在 ADR，也可以放在互相連結的聚焦架構文件。
