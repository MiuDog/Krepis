# 02-layout（`LAY`）

## 範圍

流式版面、空間版面、增量重算、display list 的產出。

## 什麼該放這裡

**「文件長什麼樣、以及那個結果怎麼交出去」的決策。** display list 的**格式**屬於這裡；
它**怎麼跨到外殼**屬於 `07-binding`。

## 決策

| 決策 | 狀態 | 主題 |
|---|---|---|
| [LAY-0001](LAY-0001-sync-background-split-and-frame-budget.md) | **Proposed** | 同步／背景的分工線與一幀預算 |

`LAY-0001` **刻意不在 P0 實測前核准**：它的正確性取決於「視窗內的增量重排 ＋ display list
產出能否穩定在一幀內完成」，那是只能量、不能推的數字。在拿到數字前核准任一方案，
等於把猜測寫成規格。

它維持 `Proposed` **不阻擋公開標頭**——邊界的形狀由 `FND-0002` 決定，分工線影響的是
內部呼叫結構。

## 排序說明

**流式與空間版面同期進行，不分先後。**

理由不是排程，是正確性：**統一模型只有一個消費者時，它的介面是猜的。** 若先只做流式，
node model 會不自覺地為流式而設計，等空間版面進來時才發現打架——這與「Krepis 需要
Jotist 作為介面逼迫函數」是同一條理由，遞迴作用在模型層。

空間版面在增量性上**比流式簡單**（流式的變更往下傳播，空間的變更是局部的），
兩者並行可讓 display list 從一開始就被兩種需求檢驗。

## 待決問題

- **增量是架構要求，不是最佳化。** 打一個字重排整份文件是 `O(n)`，文件一大即失效。
  失效傳播的粒度是什麼？段落？行？run？
- **流式與空間如何共用同一份 node tree**：流式的位置是算出來的，空間的位置是存起來的。
  這是本專案最原創、也最容易走偏的問題。
  **最鋒利的檢驗**：同一個節點同時出現在兩個視圖，在其一編輯，另一在同一幀反映。
- **display list 的格式**：連續緩衝區、零複製可讀、外殼不需要知道任何文件結構。
  版本化策略是什麼（核心與外殼可能不同步升級）？
- **一幀預算**：目標數字必須先定，否則「夠不夠快」沒有判準。
