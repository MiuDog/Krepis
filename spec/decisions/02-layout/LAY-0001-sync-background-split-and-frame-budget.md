# LAY-0001：同步／背景的分工線與一幀預算

## 狀態

**Accepted**（於 P0 實測通過後核准）

實測數據詳見 [`tasks/p0-spike-report.md`](../../../tasks/p0-spike-report.md)。

**方案 A（以視窗劃分）經實測成立**：捲動不觸發 `layout()`，$N=10{,}000$ 時視窗內處理與
Display List 產出往返 p99 為 0.42ms（佔 120Hz 預算 5.04%）。

**但本決策的核准不包含「增量性已達成」。** 該報告原宣稱打字重排為 $O(1)$，
事後複驗（同報告第六節）證實為 **$O(N)$，常數項小**：$N=10^6$ 時 p99 達 4.89ms，
佔預算 59%。spike 的 `layout()` 對全部段落重算 `y_offset`，只有 shaping 是增量的。

**影響**：方案 A 的分工線不受影響（捲動仍為 $O(\text{可見})$），但**失效傳播的正確做法
仍是未解問題**，見本目錄待決問題與 `tasks/roadmap.md` 的 P1 驗收條件 #5。

## 日期

提出：2026-08-16
接受：2026-08-16（P0 Spike 實測數據驗證通過後核准）

## 背景

`FND-0002` 已固定跨能力的執行緒模型：核心存在同步路徑與背景路徑、兩者是同一份實作的兩種
執行模式、C ABI 進入點只能由外殼 UI 執行緒呼叫、核心不得直接回呼。

**但它刻意沒有決定分工線畫在哪。** 那是版面的排程問題，且是本專案風險最高的未知之一。

「背景執行緒」不能是「所有版面都在背景執行」：若每次按鍵都需一次執行緒交接才會出現字，
那是可見延遲，直接違背輸入響應目標。所以必然是分工——問題只是線在哪。

## 候選方案

### 方案 A：以**視窗**劃分（本 ADR 傾向）

| 路徑 | 負責 |
|---|---|
| 同步（外殼 UI 執行緒） | 影響**當前視窗**的增量重排 ＋ display list 產出 |
| 背景（核心工作執行緒） | 視窗外區域、全文件範圍（總高度／捲軸）、大型重排（載入、視窗縮放） |

**優點**：判定準則是幾何的，不需啟發式；同一操作在任何文件大小下都走同一條路徑，可測。
**風險**：假設「視窗內的增量重排 ＋ display list 產出」必然能在一幀內完成。**此假設未經驗證。**

### 方案 B：以**編輯規模**劃分

小編輯走同步，大重排走背景。

**優點**：直接對應「會不會太慢」。
**缺點**：「大」的判定需要啟發式；同一操作在不同文件大小下會走不同路徑，**難以測試**，
且效能表現會出現使用者無法預期的斷崖。

### 方案 C：全部同步

**淘汰**：長文件的大型重排會卡住輸入。

### 方案 D：全部背景

**淘汰**：每次按鍵一次執行緒交接＝可見延遲。

## 為什麼刻意等實測才核准（已完成）

方案 A 的成立取決於一個**只能量、不能推**的數字：

> 對一份 N 個段落的文件，視窗內的增量重排 ＋ display list 產出，能否穩定在一幀預算內完成？

**在拿到數字前核准任何一方案，都是把猜測寫成規格**，因此本決策刻意停在 `Proposed`
直到 P0 完成。P0 已於 2026-08-16 完成，方案 A 通過。

此決策未定期間**未阻擋公開標頭的撰寫**——`FND-0002` 已固定邊界的形狀，分工線影響的是
內部呼叫結構。

## 一幀預算

目標裝置為 **120Hz**，總幀預算 **8.33ms**。使用者於 2026-08-16 提供。

**Krepis 只佔其中一段**：同一幀還有 Flutter 的事件分派、外殼 widget 的 build／layout、
Dart 端解碼 display list 與發出繪製指令。**各段的實際佔比必須實測，不得假設。**

因此 gate 設計成端到端，不依賴猜測的拆分：

| 層級 | 判準 |
|---|---|
| **主要 gate** | 打字與捲動時**不掉幀**（Flutter frame timing 直接可測，不需拆解各段） |
| **診斷指標** | Krepis 同步路徑 p99 ≤ 3ms、max ≤ 5ms。**暫定值**，待量到 Flutter 自身佔比後校正 |
| **最重要的 gate** | **耗時不隨文件長度 N 成長** |

第三條最重要：**前兩條都可能在小文件上假性通過。**

## 版面不是每幀都跑——但捲動時是

這決定 P0 該量什麼，也決定方案 A 真正的失敗模式。

| 情境 | 版面執行頻率 | 說明 |
|---|---|---|
| 打字 | 每次按鍵，約 8 次／秒 | 幀與幀之間 display list 可重用 |
| **捲動** | **每幀，120 次／秒** | **持續吞吐的情況，壓力遠高於打字** |

由此得出**背景路徑的真正職責**：

> **讓捲動時不需要跑同步版面。** 視窗外的內容若已由背景預先排好，捲動只是讀快取。

若背景路徑跟不上捲動速度，同步路徑必須補位，8.33ms 會被瞬間吃光。
**這是方案 A 最可能的失敗模式，比打字延遲更需要驗證。**

## P0 量測結果

| 項目 | 結果 |
|---|---|
| 捲動持續表現（N=10,000，1,000 幀） | p99 420μs，佔預算 5.04% ✅ |
| 打字往返（N=10,000） | p99 718μs ✅ |
| **耗時對 N 的曲線** | ❌ **未通過**——見下 |
| display list 產出 | 含於上述往返 ✅ |
| Flutter 自身佔比 | **尚未量**，診斷指標仍為暫定值 |

### 未通過項與其後果

原報告以 $N \in \{100, 1000, 10^4\}$ 三點宣告 $O(1)$。複驗拉到 $10^6$ 後證實為
**$O(N)$**（$10^5 \to 10^6$ 時耗時增為 28 倍，p99 4.89ms，佔預算 59%）。

根因為 spike 的 `layout()` 對全部段落重算 `y_offset`；只有 shaping 是增量的。

**這不否決方案 A**（捲動不觸發 `layout()`，仍為 $O(\text{可見})$），
但**失效傳播的做法是未解問題**，必須在 P1 真正解決，見本目錄待決問題。

**方法論教訓**：三個數量級以內的平坦曲線不足以宣告 $O(1)$。
複雜度主張必須測到常數項被超越為止，否則量到的是常數項而非複雜度。

### 仍待補量

**Flutter 自身在同一幀佔用多少**——上方的診斷指標（p99 ≤ 3ms）在此數字到手前維持暫定。

## 這份決策將關閉哪一道閘門

核准後，版面的呼叫結構、失效傳播的粒度、以及背景路徑的工作清單才能定案。
在此之前 `LAY-*` 的後續決策無法展開。
