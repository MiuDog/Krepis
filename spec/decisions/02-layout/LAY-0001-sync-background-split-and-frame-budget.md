# LAY-0001：同步／背景的分工線與一幀預算

## 狀態

Proposed

**本決策刻意不在 P0 實測前核准。** 它的正確性無法從推理得知——見「為什麼不現在決定」。

## 日期

提出：2026-08-16

## 背景

`FND-0002` 已固定跨能力的執行緒模型：核心存在同步路徑與背景路徑、兩者是同一份實作的兩種
執行模式、C ABI 進入點只能由外殼 UI 執行緒呼叫、核心不得直接回呼。

**但它刻意沒有決定分工線畫在哪。** 那是版面的排程問題，且是本專案風險最高的未知之一。

「背景執行緒」不能是「所有版面都在背景執行」：若每次按鍵都需一次執行緒交接才會出現字，
那是可見延遲，直接違背輸入響應目標。所以必然是分工——問題只是線在哪。

## 候選方案

### 方案 A：以**視窗**劃分（本 ADR 傾向）

| 路徑 | 負責 |
|---|---|
| 同步（外殼 UI 執行緒） | 影響**當前視窗**的增量重排 ＋ display list 產出 |
| 背景（核心工作執行緒） | 視窗外區域、全文件範圍（總高度／捲軸）、大型重排（載入、視窗縮放） |

**優點**：判定準則是幾何的，不需啟發式；同一操作在任何文件大小下都走同一條路徑，可測。
**風險**：假設「視窗內的增量重排 ＋ display list 產出」必然能在一幀內完成。**此假設未經驗證。**

### 方案 B：以**編輯規模**劃分

小編輯走同步，大重排走背景。

**優點**：直接對應「會不會太慢」。
**缺點**：「大」的判定需要啟發式；同一操作在不同文件大小下會走不同路徑，**難以測試**，
且效能表現會出現使用者無法預期的斷崖。

### 方案 C：全部同步

**淘汰**：長文件的大型重排會卡住輸入。

### 方案 D：全部背景

**淘汰**：每次按鍵一次執行緒交接＝可見延遲。

## 為什麼不現在決定

方案 A 的成立完全取決於一個**只能量、不能推**的數字：

> 對一份 N 個段落的文件，視窗內的增量重排 ＋ display list 產出，能否穩定在一幀預算內完成？

- **能** → 方案 A 成立，判定準則簡單且可測。
- **不能** → 方案 A 失效，必須退回方案 B 或重新設計版面的呼叫結構。

**在拿到數字前核准任何一方案，都是把猜測寫成規格。**

此決策未定**不阻擋公開標頭的撰寫**——`FND-0002` 已固定邊界的形狀，分工線影響的是內部
呼叫結構。因此本決策維持 `Proposed` 不構成閘門。

## P0 必須量的東西

1. **一幀預算的目標數字**先定下來（本身也是待決項，見 `tasks/roadmap.md`）。
2. 視窗內增量重排的耗時，對文件長度 N 的曲線。**重點不是絕對值，是它是否隨 N 成長**——
   若成長，代表增量性沒有真正做到，那是比分工線更根本的問題。
3. display list 產出耗時。
4. 兩者相加是否穩定落在預算內（**穩定**，不是平均——尾端延遲才是使用者感覺得到的東西）。

## 這份決策將關閉哪一道閘門

核准後，版面的呼叫結構、失效傳播的粒度、以及背景路徑的工作清單才能定案。
在此之前 `LAY-*` 的後續決策無法展開。
