建立 C++ 類別架構前，最重要的不是先畫繼承樹，而是先確定「邊界、所有權、錯誤、執行緒與相容性」。這些決策會直接決定類別應該長什麼樣子。

可以把目標整理成：

> 如何在開始實作前，建立一套足以約束類別設計、又不會過度工程化的 C++ 技術規格與專案模板？

## 一、優先確認的技術決策

| 項目 | 需要決定什麼 | 對架構的影響 |
|---|---|---|
| C++ 標準 | C++17／20／23、最低編譯器版本 | 能否使用 concepts、ranges、modules、`std::expected` |
| 目標平台 | Windows、Linux、嵌入式、跨平台 | OS 抽象層、檔案系統、編碼、動態函式庫 |
| 建置系統 | 通常使用 target-based CMake | 模組邊界、依賴方向、測試與安裝 |
| 套件管理 | vcpkg、Conan 或完全內建 | 版本鎖定、離線建置、供應鏈管理 |
| 交付形式 | 執行檔、靜態庫、動態庫、Plugin、SDK | ABI、symbol export、版本相容性 |
| 例外策略 | 使用 exception、`expected`、error code | 幾乎所有公開函式的介面形式 |
| 記憶體策略 | 一般 heap、pool、arena、固定配置 | 所有權、容器、生命週期及即時性 |
| 並行模型 | 單執行緒、thread pool、async、actor | 類別是否可共享、鎖與取消機制 |
| 效能目標 | 延遲、吞吐量、記憶體上限 | 是否真的需要模板、快取或零拷貝 |
| 相容性 | Source、API、ABI、資料格式相容 | PImpl、版本化及序列化設計 |

建議把「支援哪些編譯器與平台」寫成明確矩陣，不要只寫「跨平台」。

## 二、建立類別前先定義的規則

### 1. 所有權與生命週期

整個專案應採一致規則：

- 預設使用值語意與 RAII。
- 優先遵守 Rule of Zero。
- `std::unique_ptr` 表示唯一所有權。
- `std::shared_ptr` 只用於真正的共同所有權，不作為方便的預設。
- 非擁有參照可使用 reference、pointer、`std::span` 或 `std::string_view`，但必須能判斷生命週期。
- 避免把裸 `new/delete` 分散在業務程式碼。
- 明確規定誰建立、誰銷毀、誰可以保留物件。

### 2. 錯誤模型

選一套主要語意並保持一致：

- 無法恢復的程式錯誤：assert、contract 或終止。
- 可恢復的業務失敗：`std::expected<T, Error>` 或專案統一結果型別。
- 真正例外狀況：exception。
- 查無資料不應有時回傳 `nullptr`、有時丟例外、有時回傳錯誤碼。

錯誤型別至少應包含機器可判斷的 code；不要讓呼叫者分析錯誤訊息文字。

### 3. 執行緒模型

每個重要型別都應能回答：

- 僅限單一執行緒嗎？
- 可以由多執行緒同時讀取嗎？
- 可以同時寫入嗎？
- 鎖由類別內部還是呼叫者負責？
- 非同步操作如何取消？
- callback 在哪個執行緒執行？
- 物件銷毀時，尚未完成的工作怎麼處理？

「之後再加 thread-safe」通常會造成介面重寫。

### 4. 邊界驗證

輸入檢查集中在系統邊界：

- 使用者輸入
- 檔案與網路資料
- 第三方函式庫回傳值
- 設定檔與環境變數
- IPC、資料庫及序列化資料

內部模組在通過邊界後，應依賴強型別與不變條件，而不是每層重複驗證。

## 三、類別架構原則

- 類別應代表「責任、不變條件或資源所有權」，不必把領域中的每個名詞都做成 class。
- 優先 composition，不先建立大型繼承樹。
- 只有需要執行期替換、測試替身或外掛邊界時，才建立抽象介面。
- 把純資料 value object 與具有身分、狀態變化的 entity 分開。
- I/O、領域邏輯、儲存與 UI 不應放進同一類別。
- 建構完成的物件應盡可能立即有效，避免必須再呼叫 `Initialize()`。
- 公開介面只暴露呼叫者真正需要的內容。
- 抽象基底類別若可能透過基底指標銷毀，必須有 virtual destructor。
- 避免 public setters 破壞不變條件；改用能表達行為的方法。
- 不要為了「未來可能需要」預先增加數層 factory、manager、service 與 interface。

一個類別設計前，至少回答：

```text
責任：
不負責：
輸入與輸出：
維持的不變條件：
擁有哪些資源：
依賴哪些服務：
生命週期：
錯誤語意：
執行緒安全程度：
可否複製／移動：
擴充點：
測試方式：
```

## 四、C++ template、virtual 與 variant 怎麼選

| 需求 | 優先考慮 |
|---|---|
| 編譯期型別約束、零成本抽象 | Template + Concept |
| 執行期替換實作 | Virtual interface |
| 封閉且數量固定的型別集合 | `std::variant` |
| 小型 callback 或策略 | Function object／`std::function` |
| 穩定的 DLL／SDK 邊界 | 非模板介面、PImpl 或 C ABI |
| 不希望呼叫者重新編譯 | 避免在公開邊界暴露實作模板 |

模板不是單純的「更快版本」。它會增加編譯時間、錯誤訊息複雜度、程式碼膨脹及 ABI 限制。建議：

- 用 concept 表達必要能力。
- 不要讓模板參數接受任何型別後才在函式深處報錯。
- 公開模板保持精簡，把非型別相依實作移到普通函式。
- 必要時使用 explicit instantiation 控制編譯量。
- 不要跨 Plugin 或 DLL 邊界暴露依賴 STL 實作細節的介面。

## 五、建議的專案品質基線

至少預先準備：

- 自動格式化與靜態分析。
- 高警告等級；專案程式碼可將警告視為錯誤，第三方依賴除外。
- 單元測試、整合測試與最小 smoke test。
- Debug 模式的 AddressSanitizer、UndefinedBehaviorSanitizer；多執行緒專案另安排 ThreadSanitizer。
- Release 與 Debug 的可重現建置設定。
- 依賴版本鎖定。
- 結構化 logging；Library 不直接任意輸出 console。
- 效能 benchmark，只優化實際量測到的瓶頸。
- CI 至少涵蓋主要編譯器與目標平台。

## 六、推薦的設計順序

1. 寫出主要使用情境與不做事項。
2. 決定平台、工具鏈及交付形式。
3. 訂出效能、可靠性與相容性要求。
4. 劃分模組及依賴方向。
5. 定義模組間的資料與錯誤契約。
6. 確認所有權、生命週期及執行緒模型。
7. 對高風險技術做小型 prototype。
8. 最後才建立具體類別與模板。
