# LAY-0002 分塊參數：判準與量測報告

## 這份文件是什麼

決定 LAY-0002「尚未決定」第一項：Chunked B+ tree 的 `leaf_capacity`、`internal_fanout`
與 `merge_low_water`。

**判準寫在數字之前**（下一節）。這不是形式——先看數字再訂判準，會不自覺地挑「數字好看」的
參數而不是「符合預算」的參數，而且事後無法分辨兩者。若量測結果導致判準需要修改，
**必須在本檔明確記錄修改理由**，不得默默改掉。

執行方式：

```bash
cmake --build build --config Release --target bench_flow_sequence
```

## 判準（於 2026-08-17 量測前寫定）

### 預算推導

LAY-0001 已定：目標裝置 120Hz，總幀預算 **8.33ms**；Krepis 同步路徑診斷指標
**p99 ≤ 3ms、max ≤ 5ms**（暫定，待 Flutter 自身佔比量到後校正）。

一次按鍵的同步路徑包含：FlowSequence 結構編輯 → LocationIndex 更新 → LayoutIndex 更新 →
量測受影響 Block → display list 產出。**結構編輯只是其中一環，而且應該是最便宜的一環**——
它不做文字量測，只複製 root-to-leaf 路徑。

因此配額分配：結構編輯不得超過同步路徑預算的 **2%**（3ms × 2% = 60µs）。
取整並留餘裕後訂為下列硬門檻。

### 硬門檻（不通過即淘汰該設定）

| 編號 | 項目 | 門檻 |
|---|---|---|
| G1 | Workload 1（游標打字）**p99** | ≤ 50 µs |
| G2 | Workload 1（游標打字）**max** | ≤ 200 µs |
| G3 | Workload 4（viewport 隨機存取）**p99** | ≤ 10 µs |
| G4 | Workload 3（刪除一段）**p99** | ≤ 100 µs |
| G5 | 長度擴展：文件從 1,000 → 50,000 blocks（50×）時，Workload 1 的 p99 成長 | ≤ 3× |

G5 是**形狀判準**，不是絕對值判準：B+ tree 的成本應隨深度成長（對數），50 倍長度只增加
約一層深度。若成長接近線性，代表實作有 `O(n)` 路徑，**那是缺陷，不是調參問題**。

### 淘汰後的排序規則（依序套用）

1. **Workload 1 的 p99 最小者優先。** 游標附近打字是最高頻的操作，也是使用者最能感知的。
2. p99 差距在 **10% 以內視為平手**，改比 `leaf_capacity` **較小者優先**。
   理由：每次 COW 編輯會複製整個 leaf。`leaf_capacity = 256` 表示每次按鍵複製
   256 個 `BlockId`（4 KB）；`64` 只複製 1 KB。**延遲相近時，較小的記憶體放大倍率較好**，
   因為它同時降低配置壓力與回收佇列的負擔——而那些成本不會完整反映在單次操作的延遲上。
3. 仍平手則取 `internal_fanout` 較小者，理由同上。

### `merge_low_water` 的獨立判準

此參數只影響刪除路徑。D16 要求 split 與 merge 門檻之間有**明顯遲滯**，避免
delete／undo 在同一邊界反覆 split 與 merge。

- 硬性要求：`merge_low_water ≤ leaf_capacity / 2`。等於一半即無遲滯，直接淘汰。
- 在滿足 G4 的設定中，取**能通過 G4 的最大值**——low-water 越高，樹越緊緻，
  viewport 掃描的 leaf 數越少。
- `merge_low_water = 0`（關閉重平衡）納入量測作為對照組，**但不得作為最終選擇**：
  關閉重平衡會讓長期編輯後的樹逐漸稀疏，而 benchmark 的時間尺度看不到這個退化。

## 量測環境

- 待填：CPU、RAM、OS build
- 編譯器：MSVC（Release）
- 文件長度：10,000 blocks（參數掃描）；1,000–50,000（擴展檢查）
- 每個 workload：暖機 200 次、計時 2,000 次
- PRNG 種子固定，結果可重現

## Workload 定義

| # | 名稱 | 模擬什麼 | 為何需要 |
|---|---|---|---|
| 1 | 游標附近打字 | 在游標處插入、游標前進 | 最高頻；反覆命中同一 leaf |
| 2 | 貼上大段 | 同一區域連續插入 | 觸發連鎖 split |
| 3 | 刪除一段 | 連續 remove | 觸發 merge／redistribution（D16） |
| 4 | viewport 隨機存取 | 隨機位置 `at()` | 純讀路徑；捲動定位 |

**刻意不使用「隨機插入 N 次」**：真實編輯是局部的。隨機存取會高估樹深度成本、
低估 cache 效益，導致選出偏向淺樹的錯誤參數。

## 量測結果（2026-08-17，MSVC Release）

### 硬門檻：全部設定、全部通過，且餘裕極大

| 門檻 | 要求 | 實測最差值 | 餘裕 |
|---|---:|---:|---:|
| G1 打字 p99 | ≤ 50 µs | 4.2 µs | **12×** |
| G2 打字 max | ≤ 200 µs | 55.2 µs | 3.6× |
| G3 viewport p99 | ≤ 10 µs | 0.3 µs | **33×** |
| G4 刪除 p99 | ≤ 100 µs | 2.7 µs | **37×** |
| G5 50× 長度成長 | ≤ 3× | 1.25× | 通過 |

G5 詳細：文件 1,000 → 50,000 blocks（50 倍），打字 p99 由 1.2 µs 增為 1.5 µs = **1.25 倍**。
成長遠慢於長度，形狀為對數，**沒有 `O(n)` 路徑**。

### 關鍵發現：延遲無法區分設定

打字 p99 的差異（1.4 / 1.4 / 1.6 / 2.1 / 4.2 / 2.6 µs）**落在量測噪音範圍內**。
證據是同一組 max 值劇烈跳動且無規律：17.3 / 10.0 / 22.7 / 28.5 / 55.2 / 28.5 µs。
這些尖峰是配置器與排程器的產物，不是結構差異——若是結構差異，p50 應同向變化，
但 p50 反而是**大 leaf 較快**（0.7 vs 0.9 µs）。

**結論：全部設定都在預算的 1/12 以下，延遲不構成選擇依據。** 必須改用第二判準。

### 記憶體放大（不受計時噪音影響）

| 設定 | 節點/編輯 | leaf 承載 | leaf 位元組/編輯 |
|---|---:|---:|---:|
| leaf=8 fanout=32 | 4.00 | 8 | 128 |
| leaf=16 fanout=32 | 4.00 | 16 | 256 |
| leaf=32 fanout=32 | 4.00 | 32 | 512 |
| **leaf=64 fanout=32** | **3.00** | 64 | 1,024 |
| leaf=128 fanout=32 | 3.00 | 128 | 2,048 |
| leaf=256 fanout=32 | 3.00 | 256 | 4,096 |

節點數在 `leaf=64` 掉一階（10,000 blocks 的樹少一層）。此後節點數持平，
但 leaf 位元組持續倍增。

### Fanout 與 low-water

- Fanout 8／16／32 的打字 p99 皆為 1.2–1.3 µs；**64 起明顯變差**（1.8），
  128 最差（p99 2.5、max 74.6）。
- Low-water 8／16／24／32 的刪除 p99 皆為 0.9–1.1 µs，**量測無法區分**。
  對照組 `low=0`（關閉重平衡）為 0.9 µs，與其他無顯著差異——
  再次確認重平衡不是效能瓶頸。

## 判準修改記錄

**必須聲明：下列修改發生在看到數字之後。** 依本檔開頭的規則，理由必須寫明。

### 修改：排序規則第 2 條的前提是錯的

原文：

> p99 差距在 10% 以內視為平手，改比 `leaf_capacity` **較小者優先**。
> 理由：每次 COW 編輯會複製整個 leaf……延遲相近時，較小的記憶體放大倍率較好。

**這條規則假設「記憶體放大隨 leaf_capacity 單調遞減」，該假設不成立。**
較小的 leaf 使樹**更深**，因此每次編輯要複製**更多 internal node**。
兩個效應方向相反，總成本是 U 型而非單調——實測證實：`leaf ≤ 32` 為 4 節點／編輯，
`leaf ≥ 64` 為 3 節點／編輯。

這個錯誤是在寫判準時對演算法的誤解，**不是為了配合數字而改**。
修正後的規則不偏袒任何一端：

> **修正版第 2 條**：延遲無法區分時（差距在噪音範圍內），改比**每次編輯的節點配置數**，
> 少者優先；節點數相同時，取 `leaf_capacity` 較小者。
>
> 理由：節點配置數直接決定 reclamation queue 的操作次數（每個節點一次 Treiber push
> 加一次 delete），而 Spike 4 已證實該佇列的成本不可忽略。節點數相同時，
> 較小的 leaf 複製較少位元組，嚴格較優。

## 判定

### 定案：`leaf_capacity = 64`、`internal_fanout = 32`、`merge_low_water = 24`

**`leaf_capacity = 64`** —— 推導：

1. `leaf ≥ 128` 被 `leaf = 64` **嚴格支配**：節點數相同（3），但 leaf 大 2–4 倍。
   這個淘汰不依賴任何估計值，只用實測。
2. `leaf ≤ 32` 每次編輯多配置 **33% 的節點**（4 vs 3）。
3. 兩側都被排除，`leaf = 64` 是唯一剩下的。

**`internal_fanout = 32`** —— 實測顯示 8／16／32 無差異、64 起變差，
故上界為 32。在 8–32 之間量測無法區分，改依原則決定：**取 32**，
因為 fanout 越大樹越淺，而深度的好處在長文件才顯現（10,000 blocks 時
fanout 16 與 32 同深，但 1,000,000 blocks 時分別為 4 層與 3 層）。
benchmark 的文件長度看不到這個差別，**不能因為看不到就選錯**。

**`merge_low_water = 24`** —— 量測無法區分，依判準的原則決定：

- 硬性上界 `< leaf_capacity / 2 = 32`（等於一半即無遲滯）。
- 在 `{8, 16, 24}` 中取最大值 → **24**。
- 遲滯驗算：leaf 降到 23 觸發 merge，與鄰居 32 合併為 55；
  需 10 次插入才會回到 65 觸發 split（分為 32+33）；再需 10 次刪除才會回到 23。
  **兩個方向各約 10 次操作的緩衝**，符合 D16 對「明顯遲滯」的要求。
- 對照：若取 32，leaf 降到 31 即與 32 合併為 63，再 2 次插入就 split，
  再 1 次刪除又 merge——**會震盪**。這驗證了 `< leaf/2` 這條上界是必要的。

### 這次量測真正的產出

**分塊參數不是瓶頸。** 最緊的門檻仍有 12 倍餘裕，最鬆的有 37 倍。
這比「選到最佳參數」更有價值——它說明後續若出現 frame budget 問題，
**不應該回來調這三個數字**，該去查文字量測與 display list 產出。

同時 G5 通過（1.25× / 50×）確立了一件事：`FlowSequence` 沒有隱藏的線性路徑。
這是 LAY-0002 D4 選擇 Chunked B+ tree 而非 Vector+Fenwick 的核心主張，
**現在有實測支持，不再只是設計論證**。

## 未涵蓋的部分（誠實聲明）

- 只在單一機器、單一編譯器（MSVC Release）量測。ARM（iPad）未測。
- 未測長期編輯後的樹稀疏化——benchmark 的時間尺度看不到。
  `merge_low_water` 的選擇因此部分依賴推理而非量測。
- 未測併發讀寫下的表現（背景排版與前景編輯同時進行）。
- `internal_fanout` 在 8–32 之間的選擇依原則而非量測，長文件的假設未實測驗證。
